## Fundamentals

### What contract testing is
**Contract testing** verifies that a **consumer** and a **provider** share a compatible understanding of messages (HTTP request/response or queue messages) **without** deploying the full coupled system. Pact’s intro metaphor: you don’t set the house on fire to test the smoke alarm — you use the test button. Contracts are that test button for integrations: https://docs.pact.io/getting_started

Without contracts, teams fall back to expensive, brittle shared environments and sprawling E2E suites that still miss uncommon consumer paths.

### Consumer-driven contracts (CDC) with Pact
Pact is a **code-first, consumer-driven** tool:

1. Consumer writes a unit test against a **Pact mock provider**, specifying expected interactions.  
2. Running tests generates a **pact file** (JSON) — “contract by example,” not a full schema of every possible state.  
3. Pact file is published (Pact Broker / PactFlow / file exchange).  
4. Provider **verification** replays those interactions against the real provider (dependencies stubbed).  
5. Optionally **can-i-deploy** gates releases on verification results.

Advantage vs OpenAPI alone: only **what consumers actually use** is locked; unused provider fields can evolve. Docs stress: exercise the **real consumer client code** against the mock — don’t fire raw httpx outside the client under test.

Pact explicitly distinguishes:

- **Integration contract testing** (consumer ↔ provider compatibility) — what “contract testing” means in Pact docs.  
- **Provider contract testing** (implementation ↔ its OpenAPI doc) — useful but insufficient alone, because it doesn’t prove consumers call correctly.

### Provider-driven: OpenAPI + Schemathesis
**OpenAPI** (generated by FastAPI from routes/models) describes possible requests/responses. Tools like **Schemathesis** generate property-based tests from the schema and hit the running app, checking responses conform and hunting 500s:

- Specs: OpenAPI 2.0/3.x, GraphQL.  
- CLI: `schemathesis run <schema> --base-url ...`  
- pytest plugin / CI integration.  
- Findings include minimal `curl` reproducers.

Docs: https://schemathesis.readthedocs.io/en/stable/

This keeps the **provider honest relative to its published spec**. It does not, by itself, prove any particular consumer’s assumptions.

### Bi-directional contract testing (BDCT)
Emerging/common pattern (PactFlow and similar):

1. Provider publishes **verified** OpenAPI (self-tested via Schemathesis/Dredd/etc.).  
2. Consumer publishes Pact expectations from consumer tests.  
3. Broker **statically compares** consumer expectations to provider capability without always replaying against a live provider process.

Critical caveat from BDCT guides: if OpenAPI doesn’t match reality, the broker approves lies. **Self-verification of OpenAPI against the live app is mandatory**, not optional.

### FastAPI OpenAPI as artifact
FastAPI’s `/openapi.json` is a first-class **provider contract candidate**:

- Export in CI (`curl` or `app.openapi()`).  
- Lint (Spectral) for style/breaking-change rules.  
- Feed Schemathesis against TestClient/ASGI or a bootstrapped server.  
- Publish versioned artifact next to container images.  
- Generate TS/Python SDKs when partners need them.

Code-first drift risk: missing `response_model` → weak schemas → false confidence. Pair OpenAPI export with response models (see `02-fastapi-pydantic.md`).

## Alternatives & Tradeoffs

| Approach | Strengths | Weaknesses | When |
|----------|-----------|------------|------|
| **Pact CDC** | Locks real consumer usage; independent deploys | Process/broker learning curve | Multi-service / multi-team |
| **OpenAPI conformance (Schemathesis)** | Finds schema violations + fuzz bugs | Doesn’t prove consumer behavior | Any FastAPI service with a spec |
| **BDCT (Pact + OpenAPI)** | Scales verification; less provider replay load | Needs disciplined spec verification | Platforms with many consumers |
| **Shared E2E env only** | Feels “real” | Slow, flaky, contention | Legacy default to escape |
| **Manual Postman** | Low ceremony | Not CI-gated; drifts | Prototypes only |
| **Wiremock stubs without contracts** | Fast consumer tests | Stubs lie when provider changes | Pair with Pact or drop |
| **File-exchange pacts (no broker)** | Simple for 2 services | Versioning/can-i-deploy harder | Week 2 learning / small teams |

Fowler’s practical pyramid article recommends Pact-style CDC to reduce cross-service E2E: https://martinfowler.com/articles/practical-test-pyramid.html

## Necessity

### Failure modes if skipped
1. **Microservice version hell**: provider renames a field; consumer discovers in production.  
2. **Only E2E shared staging**: queue for the env; flaky data; can’t parallelize teams.  
3. **OpenAPI cosmetic**: `/docs` shows fields the code no longer returns; Schemathesis never run.  
4. **Consumer tests hit raw mock URLs** instead of the client → client bugs untested; pact still “green.”  
5. **Provider verification without state handlers** → can’t set up “user exists” fixtures; false failures.  
6. **BDCT without self-verification** → broker says OK; production 500s on undocumented enums.

### Must-dos
- Generate or maintain a machine-readable contract (Pact and/or OpenAPI).  
- Verify provider against consumer expectations in CI before release.  
- For FastAPI: treat `openapi.json` as a build artifact; keep it truthful via `response_model` + Schemathesis.  
- Stub provider’s downstream deps during verification (don’t call real LLM in Pact verify).

## Industry Practice

### Common (weak)
- Slack message: “we changed the response shape.”  
- Postman collection in someone’s Downloads folder.  
- Swagger UI screenshot in Confluence.  
- Consumer tests with hand-maintained fixtures that diverge from provider.

### Strong / senior
- Pact consumer tests in the FE/BFF repo; provider verify job in the API repo.  
- Pact Broker with versioned contracts + `can-i-deploy` in CD.  
- Schemathesis on PR against ASGI app or ephemeral compose stack.  
- OpenAPI diff bot comments on PRs for breaking changes.  
- Message contracts for async workers (Pact message support) when agents publish events.  
- Pact Python official FastAPI example (consumer + provider with state handlers):  
  - https://pact-foundation.github.io/pact-python/examples/http/requests_and_fastapi/test_consumer/  
  - https://pact-foundation.github.io/pact-python/examples/http/requests_and_fastapi/test_provider/

### FDE / single-service pragmatism
For a solo Week 2 take-home: **OpenAPI export + TestClient schema assertions + Schemathesis** may be enough. Introduce Pact when a second deployable consumer appears (web + mobile, or partner integration). Don’t skip mocking (file 05) — contracts complement, not replace, unit fakes.

### LLM-specific contract angles
- Tool/function JSON schemas as contracts between agent runtime and tools.  
- MCP server surfaces as providers — consumer-driven checks on tool list/call shapes (open industry question).  
- Version `api-version` or `/v1` in contracts so verification selects the right provider routes.

## Concrete Scenario

Pact getting started: contract tests assert integrations conform to a shared understanding; CDC means unused provider behavior can change freely: https://docs.pact.io/getting_started

Pact Python `requests_and_fastapi` example: consumer defines interactions and exercises real client code; provider uses `Verifier` against FastAPI with state handlers mocking DB for “user exists” / “doesn’t exist”: https://docs.pact.io/implementation_guides/python/examples

Schemathesis quick start: point at OpenAPI URL, generate property-based tests, fail on schema-violating responses or server errors — complementary provider-driven gate: https://schemathesis.readthedocs.io/en/stable/

Bi-directional flow (provider OpenAPI verified + consumer pacts compared in broker) reduces need for every provider to replay every consumer on every commit — but only if OpenAPI is true: industry BDCT writeups emphasize Schemathesis/Dredd self-check first.

Vocke’s weather-app sample in the practical test pyramid shows replacing Wiremock-only integration with Pact consumer tests that emit a shareable pact file for the provider team — same pattern for an LLM BFF consuming your FastAPI RAG service.
